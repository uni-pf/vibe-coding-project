# 发布前检查

## 一句话

它检查这次发布**会不会把不该出去的东西带出去**：密钥没泄露、接口契约和代码没漂移、
调试期的临时口子已经收掉、敏感文件没被 git 跟踪。

## 为什么要按这四项查

发布前要查的毛病有个共同点：**它们在开发和测试阶段完全不会报错**。
页面照常打开、接口照常返回 200、单元测试全绿——问题只在你把地址发出去之后才存在，
而那时候已经收不回来了（公开仓库的提交、已发出的链接地址都不可撤回）。

四项分别对应四种"不报错但已经出事"：

| 检查项 | 不查会怎样 | 什么时候真的会出事 |
| --- | --- | --- |
| 密钥泄露 | 测试时功能一点不受影响 | 仓库一公开，扫描器几分钟内就开始用它 |
| 契约漂移 | 前端照前端写、后端照后端写，各自都对 | 联调或演示时才发现字段对不上 |
| 调试残留 | 本地调试时它正是你想要的 | 它把服务端内部结构回显给了所有人 |
| 敏感文件入库 | 本地文件一直在，git status 也干净 | `.env` 进了历史，删掉文件也删不掉历史 |

## 判定原则

**每一项都要给出可证伪的证据，不能靠"我读了一遍，应该没问题"。**

- 每条结论后面必须跟**实际的命令输出、文件行号或响应原文**，不能只写"通过"
- 检查脚本自己写了什么不重要，**要看到它实际跑出来的东西**
- 报告里必须**逐项列出全部检查项**，哪怕全过也要列（否则分不清"查了通过"和"漏了没查"）
- 有疑点时必须标出来，**不许用"基本没问题""应该可以"含糊过去**

---

## 一、密钥泄露

在仓库范围内搜敏感值的**赋值或字面量**，不是搜关键词本身。

- [ ] 源码（`*.js` / `*.html` / `*.json`，排除 `node_modules/` 与 `dist/`）中不出现：
  - 形如 `password=` / `secret=` / `api_key=` / `token=` / `apikey=` 的赋值
  - 形如 `sk-` / `AKID` / `BEGIN PRIVATE KEY` / `postgres://user:pass@` 的字面量
- [ ] `.env` 及任何 `.env.*` 文件没有被 git 跟踪
- [ ] `git log --all -p` 中从未出现过上述模式（只看当前文件不够——历史里删掉值也还在）
- [ ] 若项目有 `.gitignore`，检查其中确实包含 `.env` 及其变体

**判定标准**：
- 通过 = 上述命令输出为空或只有明确的误报（如 Three.js 运行时标识符 `withCredentials`）
- 未通过 = 出现任一真实凭据模式，**必须指出文件与行号**，不要说"疑似"

**常见误报**（要能区分出来，否则会虚报未通过）：
`withCredentials`、`use-credentials`、`axios.defaults.withCredentials`
—— 这些是运行时 API 名，不是密钥。凡命中项都要人工看一遍上下文再定论。

---

## 二、接口契约一致性

**契约文件（`api-contract.md`）是唯一权威源**，代码与它不一致时，以契约为对的一方。

- [ ] 契约中声明的每一个路由，在云函数代码里都能找到对应的注册分支
- [ ] 云函数代码里注册的每一个路由，契约中都有声明（**多余的路由同样是问题**：没人知道它能用）
- [ ] 每个路由的**方法**（GET / POST / PATCH / DELETE）两边一致
- [ ] 契约中声明的错误码，代码里确实会返回

**判定标准**：
- 通过 = 契约路由集合 == 代码路由集合，且方法一一对应
- 未通过 = 存在**单边路由**（只在一方出现），必须列出是哪一条、在哪一方

**注意区分**：契约文件里的"对应关系说明表"（例如"清单原文的 `/api/hot` 对应到本项目的 `/api/objects`"）
是**历史映射记录，不是接口声明**。这类条目不算缺失，不要把它判成"契约声明了但代码没实现"。
判断依据：它是否出现在接口章节（`## N. \`METHOD /path\``）里，而不是出现在说明性表格里。

---

## 三、调试残留

只针对**云函数 / 服务端代码**。

- [ ] 不存在 `return event` / `return context` / `return process.env` 这类整体回显
- [ ] 不存在把 `process.env` 的内容塞进响应体的代码
- [ ] 不存在"临时把原始错误带回响应"的调试代码
  （典型形式：`error: err.message` 直接进响应，且原文是英文内部结构信息）
- [ ] 响应里只出现**自己挑选过的字段**，不出现整个请求对象

**判定标准**：
- 通过 = 响应构造只依赖显式选定的字段，且服务端错误只返回中文提示
- 未通过 = 出现任一整体回显或原始错误透传，**必须指出文件与行号**

**为什么这条最危险**：网关会在请求头里注入临时凭据。
回显 `event` 或 `process.env` 等于把凭据一起发给了调用方，
而页面功能**完全正常**——只有去看响应体的人才会发现。

---

## 四、敏感文件跟踪

- [ ] `git ls-files` 里不出现：`.env`、`.env.*`、`*.pem`、`*.key`、`.git-credentials`、`credentials.json`
- [ ] 仓库根有 `.gitignore`，且覆盖了环境变量文件与依赖目录
- [ ] 如果一个路径"本来存在但被忽略"，用 `git check-ignore -v <path>` 确认忽略规则确实生效
  （只看 `.gitignore` 里写了什么不算——要确认规则真的匹配到了）

**判定标准**：
- 通过 = `git ls-files` 输出中无敏感路径，且忽略规则经 `check-ignore` 实测生效
- 未通过 = 敏感文件出现在已跟踪清单里，必须给出路径

---

## 输出格式

每次检查输出一张表，**逐项列出，不允许省略没问题的项**：

```
## 发布前检查结果 · YYYY-MM-DD

| # | 检查项 | 结论 | 证据 |
|---|--------|------|------|
| 1 | 密钥泄露 | 通过 / 未通过 | 命令 + 输出摘要 / 文件:行号 |
| 2 | 契约一致性 | 通过 / 未通过 | 两侧路由集合的差异 |
| 3 | 调试残留 | 通过 / 未通过 | 文件:行号 |
| 4 | 敏感文件跟踪 | 通过 / 未通过 | git ls-files 结果 / check-ignore 输出 |

### 未通过项明细
（每一项写清：在哪、是什么、为什么算问题、建议怎么修）

### 结论
- 可以发布 / 不建议发布（存在 N 项未通过）
```

**报告纪律**：
- 未通过项必须写在**表格里的结论列**，不能只藏在末尾段落
- 不许把"没查"写成"通过"；跳过某条要在证据列明写"未检查"
- 全部通过时也要输出完整的四行表格

## 调用记录

每次调用后，把结果追加到项目根目录的 `SKILL-CALL-LOG.md`，格式：

```
## YYYY-MM-DD · 第 N 次调用
- 调用对象：（哪个版本 / 哪次发布）
- 结论：通过 / 未通过（未通过要写清哪一项、实际看到的是什么）
- 证据：（截图路径或命令输出）
```

没有记录的调用等于没调用——将来复查的人只能靠这份记录判断"当时到底查没查"。
