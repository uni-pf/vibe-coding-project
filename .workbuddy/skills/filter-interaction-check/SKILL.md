# 筛选交互检查

## 一句话

它检查一次筛选操作在三种情况下有没有都给出明确结果：
**筛得出东西时列表和计数同步更新、筛不出时给出空态文案而不是留白、清空条件后能完整回到初始列表。**

## 为什么要按这三项查

筛选最常见的毛病不是"筛错了"，而是"筛完以后没交代"。
筛得出东西时一切正常，一旦筛不到，页面就成了空列表——没有报错、没有卡顿，
只是什么都不显示。用户看到的是一片白，无法判断到底是"没有匹配的"还是"页面坏了"。

所以这三项缺一不可：**有结果**证明筛选生效，**无结果**证明筛选失败时也有人接住，
**清空恢复**证明这件事是可逆的、用户不会因为试了一次就回不去。

## 检查方式

不要靠读代码下结论。在浏览器里**实际操作一遍**，看页面上真实出现了什么。
每一项都要有肉眼可见的结果（截图或 DOM 取值），不接受"代码里写了所以应该没问题"。

---

## 一、有结果

- [ ] 列表条数 = 命中条数，不多不少
- [ ] 计数文案跟着变（例如"共 3 件"→"共 1 件"）。计数只能有一个来源，不能某处写死
- [ ] 卡片上的序号是筛选结果里的序号，还是原始数据里的编号——两种都行，但要**明确是哪种且不跳号**
- [ ] 关键词本身在结果里能被看到（否则用户不知道自己筛的是什么）

## 二、无结果

- [ ] **必须显示空态文案**，不能只是一片空白。这是最容易漏的一项
- [ ] 文案要说清"没有匹配的"而不是"这里什么都没有"——
      「数据本来就是空的」和「筛完了没有匹配的」是两件事，混着说会误导
- [ ] 文案里给出恢复路径（清空关键词 / 换个词）
- [ ] 计数显示 0，且与空态同时出现

## 三、清空恢复

- [ ] 清空输入框后，列表完整回到初始状态：条数、顺序、序号都与筛选前一致
- [ ] 计数回到总数
- [ ] 空态消失，不能残留
- [ ] 连续快速输入再快速删除，结果不残留、不错乱（防抖或竞态处理）

---

## 四、可访问性（加练项）

- [ ] 输入框有关联的 label（可见文字或视觉隐藏的 `<label>`），不能只靠 placeholder
- [ ] 结果数量变化通过 `aria-live="polite"` 播报，读屏用户能听到"筛出 1 件"
- [ ] 无结果时同一区域也要播报"没有匹配的物件"，不能只在视觉上变
- [ ] 键盘全程可达：Tab 能到输入框，Esc 能清空，输入时焦点不丢
- [ ] 列表被清空重渲染时，焦点不会被甩到 `body`
- [ ] 空态文字与背景的对比度达到 WCAG AA（正文 4.5:1）

---

## 调用记录

每次调用后，把结果追加到项目根目录的 `SKILL-CALL-LOG.md`，格式：

```
## YYYY-MM-DD · 第 N 次调用
- 调用对象：（哪个页面 / 哪个功能）
- 结论：通过 / 未通过（未通过要写清哪一项、页面上实际看到的是什么）
- 证据：（截图路径或命令输出）
```

没有记录的调用等于没调用——这句话是给将来复查的人看的。
